# План рефактора архитектуры

Цель — сделать TopDps простым для расширения новыми классами и специализациями, не размазывая class-specific логику по общему движку.

## Ограничения этого PR

- Не менять текущие приоритеты Retribution Paladin.
- Не менять условия использования текущих способностей.
- Не добавлять lookahead при выборе способности.
- Не менять версию аддона.

## План

1. Перевести внутренний namespace окончательно на `TopDps` и убрать старые имена `RpalTopDps` из runtime-кода и UI-объектов.
2. Разделить общий движок на отдельные обязанности:
   - `ActionBarService` — обнаружение кнопок и способностей;
   - `ReadinessService` — готовность, cooldown и range;
   - `ContextBuilder` — построение контекста ротации;
   - `RotationEngine` — только выбор первой подходящей способности по приоритету;
   - `CombatTracker` — подсчёт активных целей.
3. Добавить базовый `SpecProvider` с общими реализациями и декларативным описанием способностей.
4. Переделать `SpecRegistry` в индекс `classToken + talentTab`, чтобы специализации не определяли себя перебором `IsActive()`.
5. Добавить `SpecManager`, который централизованно определяет и кеширует активную специализацию и обновляет её только по релевантным игровым событиям.
6. Перевести Retribution Paladin на новый provider-контракт без изменения ротации.
7. Убрать class-specific обработку экипировки из `Bootstrap`; события должны делегироваться активному provider.
8. Автоматизировать подключение файлов специализаций в `.toc` через генератор, который сканирует `Specs/<Class>/*.lua`; release workflow запускает генератор перед сборкой архива.
9. Обновить документацию по добавлению нового класса/специализации.
10. Проверить Lua/XML синтаксис и то, что текущая Retribution-логика сохранилась.

## Подготовка к lookahead

Lookahead будет отдельной фичей после этого PR.

В этом рефакторе `ReadinessService` получает отдельные API для остатка cooldown и GCD. Текущий `RotationEngine` продолжает выбирать только способность, которая считается готовой по существующим правилам.

В будущем lookahead можно будет реализовать внутри слоя готовности/выбора кандидата, сравнивая время до окончания GCD и cooldown более приоритетной способности, не меняя providers и структуру специализаций.

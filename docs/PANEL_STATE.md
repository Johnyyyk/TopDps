# Состояния панели и чтение аур

## Тип `state`

`state` предназначен для бинарных условий персонажа, которые нельзя корректно выразить через обычную WoW-ауру или cooldown способности.

Типичные случаи:

- призван ли нужный питомец;
- соответствует ли активный питомец специализации;
- наложена ли нужная временная чарка на оружие;
- другие постоянные условия подготовки персонажа, не представленные через `UnitBuff`/`UnitDebuff`.

Не следует использовать `state` для обычных бафов, дебафов, проков и cooldown. Если состояние доступно через `UnitBuff`/`UnitDebuff`, оно должно оставаться `aura`. Например, печать паладина остаётся `SELECTABLE_BUFF`, а временный боевой прок остаётся элементом группы `PROCS`.

Запись `state` обязана определить `getState`. Допустимые результаты:

```lua
getState = function()
    return true
end
```

или:

```lua
getState = function()
    return {
        active = true,
        statusText = nil,
        icon = nil,
        spellId = nil,
        unitName = nil,
        stacks = 0,
        showStacks = false,
    }
end
```

`active` является единственным обязательным полем табличного результата. Временные параметры (`duration`, `remaining`, внутренний cooldown) намеренно не входят в контракт `state`: для временных эффектов следует использовать существующие типы панели.

По умолчанию `state` получает:

- группу `STATES`;
- категорию панели `BUFFS`;
- поведение `REQUIRED_STATE`.

В обычном заблокированном режиме выполненное required-state скрыто, а невыполненное выводится как предупреждение. В preview отображаются оба состояния.

## Применимость элемента панели

Любой декларативный элемент панели может определить необязательный callback `isApplicable`.

Он используется только для ситуаций, когда само требование временно неприменимо, и не должен подменять реальное состояние элемента. Например, на маунте требование к призванному питомцу можно скрыть через `isApplicable`, но нельзя возвращать из `getState` ложное `active = true`.

То же правило сохраняет семантику типов: если Soul Link является реальной аурой, он остаётся `aura`, а `isApplicable` только скрывает требование в ситуации, когда проверять его бессмысленно.

```lua
isApplicable = function()
    return not IsMounted()
end
```

Для переходов, где WoW API обновляет связанные состояния не одновременно, можно задать `applicabilityGrace` в секундах. Задержка применяется только при переходе `isApplicable` из `false` в `true`; первоначально применимый элемент не задерживается.

```lua
isApplicable = function()
    return SomeRequirementIsApplicable()
end,
applicabilityGrace = 0.5,
```

Если рассинхрон относится к конкретной игровой механике, предпочтительнее скрыть его внутри domain-helper этой механики, а не увеличивать глобальный grace. Например, Warlock отдельно отслеживает короткий переход питомца при посадке/спешивании с маунта.

Ошибки `isApplicable` изолируются через `pcall` и журналируются один раз до изменения текста ошибки.

## `AuraService`

`Engine/AuraService.lua` является общей read-only точкой чтения `UnitBuff`/`UnitDebuff` для панели и ротаций специализаций.

Он предоставляет:

- чтение одной ауры;
- поиск ауры на unit с `ownOnly`;
- индекс аур unit для повторных проверок;
- поиск по spell ID с fallback по имени способности для совместимости с клиентами 3.3.5a/private server.

Class/spec-код не должен зависеть от `CooldownTracker` только ради чтения аур и не должен без необходимости дублировать собственные циклы по `UnitBuff`/`UnitDebuff`. Для ротаций с большим количеством DoT/прок-проверок следует использовать `AuraService` напрямую.

## `EquipmentService`

`Engine/EquipmentService.lua` является общей read-only точкой для временных чарок оружия.

В WoW 3.3.5a `GetWeaponEnchantInfo()` сообщает наличие временной чарки, оставшееся время и количество зарядов, но не идентификатор её типа. Поэтому тип эффекта определяется по локализованной строке временной чарки в скрытом tooltip экипированного оружия.

Сервис разделяет ответственность следующим образом:

1. `GetWeaponEnchantInfo()` сообщает, есть ли temporary enchant и его таймер/заряды;
2. скрытый equipment-tooltip даёт локализованное имя эффекта;
3. вызывающий class/spec-код передаёт семейство допустимых spell ID;
4. сервис получает их локализованные имена через `GetSpellInfo()` и сопоставляет с tooltip;
5. конкретные Spellstone, Firestone, шаманские imbue и другие class-specific эффекты внутри `EquipmentService` не хранятся.

Изменения temporary enchant отслеживаются через `UNIT_INVENTORY_CHANGED`. После события tooltip перечитывается с задержкой и повторной попыткой, потому что в клиенте 3.3.5a `GetWeaponEnchantInfo()` и строки equipment-tooltip могут обновляться не одновременно. Между событиями результат tooltip кэшируется и не сканируется каждый update панели.

Class/spec-код не должен самостоятельно читать `GetWeaponEnchantInfo()` или создавать скрытые tooltip ради определения временной чарки. Для этого используется `EquipmentService`.

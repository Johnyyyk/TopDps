# Правила работы с TopDps

Этот файл задаёт обязательный процесс работы с репозиторием для AI-ассистента. Подробная архитектура, правила добавления специализаций и технические чек-листы находятся в `CONTRIBUTING.md`.

## Перед началом любой задачи

1. Прочитать issue/описание задачи целиком и проверить актуальное состояние `develop`.
2. Прочитать релевантные разделы `CONTRIBUTING.md` и существующий код затрагиваемой подсистемы.
3. Перед добавлением новой абстракции убедиться, что задача не решается существующими Core/Engine primitives или spec-level логикой.
4. Для игровых механик ориентироваться только на WotLK 3.3.5a. Спорные механики, spell ID, ранги, таланты, glyph/set bonus и ограничения API перепроверять по надёжным источникам и фактическому API клиента.

## Архитектурные правила

- Core/Engine должны оставаться универсальными и не содержать class-specific условий без объективной общей механики.
- Class/spec-specific решения должны оставаться в provider, class common-модуле или декларативных данных панели.
- Не добавлять compatibility proxy, monkey-patch, поздние override-файлы и дублирующие реализации.
- Не добавлять абстракции «на всякий случай».
- Настройки и UI по возможности описывать существующими декларативными контрактами.

## Git и процесс работы

- Обычная разработка начинается от актуального `develop` в отдельной feature/fix-ветке.
- Прямые изменения `develop` допустимы только по явной просьбе пользователя.
- Коммиты и описания вести на русском языке.
- Коммиты должны быть осмысленными; не дробить одну законченную правку на nano-коммиты.
- Не использовать squash/rebase для уже сформированной feature/fix-истории; сохранять отдельные осмысленные коммиты и merge-коммит.
- Не сливать PR и не закрывать issue до явного подтверждения пользователя после ручной проверки, если пользователь не попросил сделать это сразу.

## Обязательная перепроверка перед передачей результата

Фраза «готово» допустима только после отдельного self-review, а не сразу после реализации.

1. Повторно прочитать требования issue и сверить реализацию пункт за пунктом.
2. Просмотреть полный diff относительно `develop` как ревьюер, отдельно от прохода реализации.
3. Проверить архитектурную границу Core/Engine/spec/panel и отсутствие лишнего дублирования.
4. Запустить все доступные автоматические проверки проекта и релевантные smoke/regression tests.
5. Проверить, нужны ли новые тесты для изменённой механики, edge cases и regressions.
6. Проверить влияние на уже существующие специализации и общие подсистемы.
7. Проверить настройки, defaults, SavedVariables/schema implications, локализацию, TOC и документацию, если они затронуты.
8. Для добавления или существенного изменения специализации обязательно пройти полный чек-лист из `CONTRIBUTING.md`, включая отдельные проходы по ротации, способностям и боевой панели.
9. После всех исправлений ещё раз просмотреть итоговый diff, чтобы self-review относился к финальному состоянию кода.

## Обязательный аудит специализации

При добавлении или существенном изменении специализации нельзя ограничиваться тем, что код работает и тесты проходят. Нужно отдельно:

- перепроверить полный набор реально используемых способностей и все их ранги/ID;
- проверить, что для каждой способности включены только действительно нужные параметры readiness/refresh/range/state tracking;
- проверить, что лишние metadata/callbacks и вычисления отключены или не добавлены;
- составить полный набор элементов панели: обязательные бафы/states, проки, offensive cooldowns, defensive, utility, ресурсы, предметы/трини;
- затем сделать второй проход по панели с позиции пользователя и убрать визуальный шум;
- для каждого defensive/utility элемента отдельно решить: включён по умолчанию, доступен но выключен по умолчанию, либо вообще не нужен на панели;
- отдельно проверить `showDuration`, `showStacks`, proc sound, applicability/talent requirements, behavior/category/order и default allowlist;
- не включать элемент по умолчанию только потому, что способность существует у класса.

Подробный Definition of Done для этого прохода находится в разделе `Чек-лист реализации и проверки специализации` в `CONTRIBUTING.md`.

# Разработка TopDps

TopDps устроен так, чтобы логика конкретного класса и специализации была отделена от общего движка, проверки готовности способностей, хранения настроек и интерфейса.

## Структура проекта

```text
Core/           namespace, настройки, SavedVariables, API-обёртки и логирование
Engine/         ротация, готовность способностей, контекст боя и сбор состояния панели
Specs/          provider-контракт, registry, определение активного спека и сами специализации
Cooldowns/      декларативные данные панели, тринь и equipment proc
Presentation/   подсветка, центральные иконки, боевая панель и звуки проков
UI/             общие настройки, ротация, панель, отладка и кнопка миникарты
Vendor/         встроенные сторонние или адаптированные визуальные компоненты
Textures/       текстуры аддона
tools/          генератор spec-файлов TOC и проверки проекта
Bootstrap.lua   инициализация, игровые события и retry определения специализации
TopDps.toc      манифест, версия и порядок загрузки файлов
```

Общее направление зависимостей:

```text
SavedVariables -> Settings -> Engine -> Presentation
```

Не следует добавлять compatibility proxy, поздние override-файлы или monkey-patch, которые повторно заменяют уже объявленные методы Core/Engine/Presentation. Для одного поведения должна существовать одна основная реализация.

## Как определяется специализация

`SpecManager` определяет класс персонажа и читает количество очков в трёх ветках талантов. Активной считается ветка с наибольшей долей очков от их общего количества. Если максимальная доля совпала у нескольких веток, специализация считается неопределённой.

Определение выполняется по игровым событиям, которые могут изменить персонажа или состояние talent API. Постоянного polling раз в секунду нет.

После загрузочных экранов WoW 3.3.5a иногда временно возвращает пустые данные талантов. В таком состоянии `SpecManager` возвращает `not_ready`, не сбрасывает уже выбранный provider, а `Bootstrap` повторяет определение с интервалом `0.5` секунды до `10` попыток. После появления корректных данных состояние обновляется обычным способом.

Общий `RotationEngine` не знает ничего о паладине, воине или другом классе. Он получает активный provider из `SpecManager`, его приоритеты и настройки, после чего проверяет способности через общий `ReadinessService`.

## Добавление нового класса или специализации

1. При необходимости создайте `Specs/<Class>/Common.lua` с общими константами класса.
2. Создайте `Specs/<Class>/<Spec>.lua`.
3. Создайте provider через `TopDps.SpecProvider:Create(...)`.
4. Укажите как минимум:
   - `id`;
   - `classToken`;
   - `talentTab` от `1` до `3`;
   - `categories`;
   - `abilities` со списками `spellIds`;
   - `GetPriority(context)`.
5. Зарегистрируйте provider через `TopDps.SpecRegistry:Register(provider)`.

Пример метаданных:

```lua
local Fury = TopDps.SpecProvider:Create({
    id = "WARRIOR_FURY",
    classToken = "WARRIOR",
    talentTab = 2,
    categories = {
        "bloodthirst",
        "whirlwind",
    },
    abilities = {
        bloodthirst = { spellIds = { 23881 } },
        whirlwind = { spellIds = { 1680 } },
    },
})
```

`SpecProvider` содержит стандартные реализации проверки range, ready entries, каталога spell ID/name и других общих операций. Специализация переопределяет только действительно специфичное поведение.

Добавление нового provider не должно требовать class-specific условий в `Core`, `Engine` или общем UI. Если такое условие требуется, сначала стоит проверить, нельзя ли выразить его через provider или декларативные данные.

## Настройки ротации специализации

Для каждой категории из `provider.categories` автоматически создаётся переключатель `ability_<category>`. Полного spec-level `enabled` больше нет: включение самой ротации хранится отдельно для персонажа в `TopDpsCharDB.rotationEnabled`.

Дополнительные настройки специализации задаются декларативно в `provider.settings`. Поддерживаются типы:

- `checkbox`;
- `slider`;
- `dropdown`;
- `header`.

`SpecRegistry` проверяет дубликаты ключей, допустимые значения dropdown и границы/step слайдеров. Страница `UI/RotationOptions.lua` строится динамически по `provider:GetSettingsDefinition()`, поэтому для обычной настройки нового спека отдельный UI-код не нужен.

Настройки ротации provider хранятся в `TopDpsDB.specs[provider.id].rotation`.

`RotationEngine` применяет проверки в следующем порядке:

- включена ли ротация персонажа;
- разрешён ли общий `mode`;
- доступен ли активный provider;
- включена ли категория через `ability_<category>`;
- разрешена ли категория через `provider:IsCategoryAllowed(category, context)`;
- есть ли готовые действия через `ReadinessService`.

## Боевая панель

Панель независима от ротации. Общий переключатель панели хранится в `TopDpsCharDB.panelEnabled`.

Глобальные визуальные параметры панели находятся в `TopDpsDB.global.panel`, а настройки конкретной class/spec-комбинации — в `TopDpsDB.cooldownSpecs["<classToken>:<talentTab>"].panel`.

Текущие группы панели предназначены для:

- обязательных собственных бафов;
- активных проков;
- защиты и утилити;
- тринь и дополнительных кулдаунов.

`CooldownTracker:Update()` является единой точкой сбора состояния и обрабатывает spell, aura, counter, trinket и equipment proc. Не следует создавать отдельные файлы, которые повторно заменяют этот метод.

Порядок gate панели:

```text
panelEnabled -> mode -> combatOnly / unlocked preview -> content -> display
```

Разблокированная панель может обходить `combatOnly` для preview, но не может обходить `MODE_DISABLED`.

## SavedVariables

Текущая schema version: **4**.

```text
TopDpsDB
  schemaVersion
  global
    mode
    minimap
    rotation
      highlightStyle
      cooldownLookahead
      centerIcons
    panel
    debug
  specs
    <provider.id>
      rotation
  cooldownSpecs
    <classToken:talentTab>
      panel
  cooldownSpecTemplate
    panel

TopDpsCharDB
  rotationEnabled
  panelEnabled
```

`addon.db` напрямую указывает на `TopDpsDB.global`. Старые плоские ключи через proxy не поддерживаются.

Версия 2.0.0 намеренно не мигрирует SavedVariables версий 1.x. Если `TopDpsDB` не соответствует текущей schema, создаётся новый root с актуальной структурой. `RpalTopDpsDB` больше не используется.

При изменении структуры БД увеличивайте `SCHEMA_VERSION` и обновляйте этот раздел. Возвращать legacy migration/proxy ради совместимости с 1.x не нужно.

## Готовность способности и cooldown lookahead

`Engine/ReadinessService.lua` отвечает за usability, range и cooldown.

Cooldown lookahead позволяет рекомендовать способность немного раньше полного окончания её отката. Значение хранится в `TopDpsDB.global.rotation.cooldownLookahead`.

Текущие границы:

- минимум: `0` секунд;
- максимум: `0.5` секунды;
- шаг: `0.05` секунды;
- значение по умолчанию: `0.15` секунды.

Cooldown длительностью GCD по-прежнему не блокирует рекомендацию. Специфические правила готовности можно переопределять через методы provider, не добавляя class-specific код в `ReadinessService`.

## Автоматическое подключение специализаций

WoW 3.3.5a не умеет во время работы аддона просканировать папку и загрузить новые Lua-файлы: список файлов должен быть известен из `.toc` заранее.

Поэтому список специализаций генерируется автоматически:

```text
python3 tools/generate_toc.py
```

Генератор сканирует `Specs/<Class>/*.lua`, загружает `Common.lua` первым и обновляет блок между маркерами `TopDps-Specs-Start/End` в `TopDps.toc`.

CI выполняет `python3 tools/generate_toc.py --check` и не даёт смержить устаревший `.toc`. Release workflow перед упаковкой ещё раз запускает генератор.

## Где вручную менять ротацию

Текущая эталонная реализация — `Specs/Paladin/Retribution.lua`.

В начале spec-файла находится декларативное описание поддерживаемых способностей. Таблица `PRIORITY` задаёт основной порядок категорий для конкретных режимов. Специальные условия вроде execute, проков, дистанции или типа цели остаются методами этого же provider.

Для изменения самой ротации не требуется трогать `RotationEngine`, `SpecManager` или UI.

## Проверки проекта

Обычный workflow проверяет:

- актуальность автоматически сгенерированного блока специализаций в TOC;
- согласованность версии проекта;
- отсутствие legacy-архитектуры настроек и удалённых override-файлов;
- синтаксис Lua 5.1;
- XML.

`tools/check_settings_architecture.py` специально защищает архитектуру 2.0.0 от возврата старых flat-ключей, migration/proxy API и файлов, которые раньше переопределяли основные методы.

Release workflow дополнительно собирает ZIP и проверяет его содержимое до создания GitHub Release.

## Ручной smoke-test перед релизом

CI не заменяет проверку в клиенте WoW 3.3.5a. Перед merge `develop -> main` проверьте:

1. Чистую установку без `TopDpsDB` и `TopDpsCharDB`.
2. Запуск поверх SavedVariables от 1.1.0 и корректное создание новой структуры.
3. `/reload` после изменения настроек.
4. Двух разных персонажей: `rotationEnabled` и `panelEnabled` должны быть независимыми для каждого.
5. Независимые комбинации ротации и панели: on/off × on/off.
6. Все режимы: везде, подземелья и рейды, только рейды, выключено.
7. Панель locked/unlocked и `combatOnly` внутри и вне боя.
8. Проки, звуковые уведомления, трини и equipment proc.
9. Оба стиля подсветки и центральные иконки.
10. Изменение cooldown lookahead и фактическое влияние настройки на момент рекомендации.

## Особенности WoW 3.3.5a

- Аддон рассчитан на интерфейс версии `30300`.
- В `Core/GameApi.lua` находятся обёртки совместимости для различий API клиента 3.3.5a и отдельных private server сборок.
- Сейчас предполагается использование стандартных панелей действий Blizzard.
- Talent API после загрузочных экранов может временно возвращать пустые данные, поэтому определение специализации должно учитывать состояние `not_ready`.

## Отладка

Страницу отладки можно полностью скрыть в `Core/Namespace.lua`:

```lua
addon.SHOW_DEBUG_OPTIONS = false
```

При изменении определения способностей или совместимости с WoW API включайте отладочный журнал и проверяйте распознанные ID способностей, активный provider и текущее состояние рекомендации непосредственно в игре.

## Ветки и порядок слияния

`main` и `develop` — отдельные долгоживущие ветки. Их нельзя синхронизировать fast-forward перемещением ref.

Рабочая схема:

1. Новая feature/fix-ветка создаётся от актуального `develop`.
2. Готовая работа сливается обычным merge-коммитом в `develop`.
3. В `main` попадают только проверенные релизные изменения через merge `develop -> main`.
4. Если после релиза изменения из `main` нужно вернуть в разработку, выполняется отдельный merge `main -> develop`.
5. Для feature/fix и release merge сохраняется история отдельных коммитов: squash и rebase не используются.

Так история Git явно показывает границы фич, исправлений и релизов.

## Версионирование и релизы

Проект использует семантическое версионирование `MAJOR.MINOR.PATCH`.

- `PATCH` — исправления без новых пользовательских возможностей.
- `MINOR` — новые совместимые функции, настройки, классы или специализации.
- `MAJOR` — крупные несовместимые или концептуальные изменения.

Перед релизом одна и та же версия должна быть указана в:

- `README.md`;
- `TopDps.toc`;
- `Core/Namespace.lua`.

`tools/check_version.py` проверяет их согласованность в обычном CI и в release workflow.

После merge релизного `develop -> main` workflow читает версию из `TopDps.toc` и, если соответствующего релиза ещё нет, автоматически создаёт:

- тег и GitHub Release `vX.Y.Z`;
- архив `TopDps-X.Y.Z.zip`.

README, документация, commit messages и описание релизов ведутся на русском языке.
